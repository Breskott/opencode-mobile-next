- Contract problems (PROC-20):
  - **Galleries reduced by a later owner decision, not a defect.** The frozen spec's "Galleries
    required" (§8.4) asks for 40 PNGs across five sizes, Arabic RTL and 2.0 text; the task's owner
    decision dated 2026-09-27 (later than the spec, R15) drops Arabic and text-2.0 galleries
    entirely and keeps only two sizes (412×915 phone, 1280×800 wide). The gallery here renders the
    spec's seven declared states at those two sizes, light and dark (7 × 2 × 2 = 28 PNGs), and
    leaves out the RTL/text-2.0/other-size rows. STANDARDS.md TEST-9 (the older, broader gallery
    matrix) is superseded by the same decision for this unit.
  - **"Copy is disabled" on empty (spec States table) vs `KitIconButton.copy`'s API.** The frozen
    API names `KitIconButton.copy` as the mechanism for the "copied" state, but that widget has no
    `onPressed`/disabled path (its copy variant is always enabled). Read "Copy is disabled" as
    STATE-8's documented alternative ("or to hide the button", KitIconButton.md) when the text is
    empty: the empty state hides Copy entirely rather than showing a dead control, and the visible
    "Empty" text already explains why. Not escalated; a reasonable reading of an existing rule,
    not a rule conflict.
  - **`kitCodeChanges` duplicates the existing `reviewCounts` key's exact string** (`"{added}
    added, {removed} removed"`, `lib/l10n/app_en.arb`). The frozen spec's ARB list (§ "Kit copy")
    explicitly names `kitCodeChanges` as a new key, so it was added as specified (COPY-11 asks the
    coordinator to dedupe copy across parts; flagging here rather than silently reusing
    `reviewCounts`, which the spec does not mention).
- New kit parts (KIT-3): none (`KitCodeBlock`, `KitCodeKind`, `KitCodeHighlight` are the one unit
  this wave assigns; no other class was introduced).
- Map items (EVID-11): n/a — no map pages assigned.

## 7. NOT proven

- Not run on a device or emulator (coordinator/checkpoint work, R19/R20).
- `.fill` with `wrap: true` is not proven at scale: the virtualised `ListView.builder` uses a
  fixed `itemExtent` sized from one unwrapped mono line, so a wrapped line in `.fill` needing more
  than one visual row is not measured or tested; the proven, primary `.fill` scenario (diff/log
  viewers) is unwrapped with line numbers, which the tests and gallery (`fill_find`) cover.
- Redaction of `.fill` text is display-safe (`KitRedact.text` runs before rendering, and the copy
  path redacts), but `marks`/`activeMark` offsets are the caller's original, unredacted
  coordinates; if a `.fill` text actually contains something `KitRedact` masks (changing the
  string's length), a mark whose range sits after the masked span could point at the wrong text.
  Not exercised: fill content in the app (diffs, logs) is not expected to carry live secrets in
  the first place, and this is a display-time edge case, not a leak (the text itself is still
  redacted).
- The horizontal scroller's keyboard behaviour ("focusable only when it can scroll") relies on
  Flutter's default `Scrollable` handling; no test isolates that a scroller with nothing to scroll
  is skipped in Tab order.
- Full repository suite (`flutter test --concurrency=1` over all of `test/`) was not run — out of
  a kit unit's scope; that is the coordinator's wave-checkpoint gate (AGENTS.md rule 6).
  `test/design_standard_test.dart` and `test/l10n_coverage_test.dart` were not run directly: this
  unit adds no `Text('…')`/`tooltip:` literals (grepped, none) and touches no migrated screen, so
  neither ratchet's baseline is expected to move; not independently confirmed by a run.
- Hover/focus looks of the header's Wrap and Copy controls are `KitIconButton`'s own, already
  proven in its unit; this gallery shows only their default/selected looks inside `KitCodeBlock`,
  not hovered/focused compositions.
