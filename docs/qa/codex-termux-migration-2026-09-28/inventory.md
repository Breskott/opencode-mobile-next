# Managed Termux migration inventory — 2026-09-28

This is source-based feasibility evidence. No phone or emulator was accessed for this inventory. The delivery README defines which offers are implemented; an inventory offer is not a claim of an implemented importer.

## Managed roots and compatibility

`TermuxBridge.termuxHome` is `/data/data/com.termux/files/home`; the managed Ubuntu is named `opencode-ubuntu`. Its rootfs is one of `$PREFIX/var/lib/proot-distro/containers/opencode-ubuntu/rootfs` and the older `$PREFIX/var/lib/proot-distro/installed-rootfs/opencode-ubuntu`. Reject ambiguity rather than guess. `/root` below means the home **inside that Ubuntu**, not Termux's own home. Native Termux installations and arbitrary user roots are separate manual cases.

The same `openCodeUbuntuSetupScript` installs both Termux and built-in tools. `TermuxRuntime` pins OC1 **1.18.32** and OC2 **2.0.10**; an actual installation may differ, so inspect its runtime/version before making a compatibility claim. A different version is not permission to upgrade or downgrade the source.

Managed projects are `/root/projects`. Built-in projects physically live in `<filesDir>/projects`, bound to `/root/projects`. Preserving that guest path avoids rewriting normal project references. Worktrees with external `.git` pointers, absolute symlinks, external submodules, and repositories whose origin points into AI Team storage need explicit review; copying their visible directory alone is not a complete repository migration.

OC1 defaults: `/root/.config/opencode`, `/root/.local/share/opencode`, `/root/.local/state/opencode`, `/root/.cache/opencode`. OC2 Termux may use those same defaults **or** isolation, selected by Termux `~/.oc/opencode2-data-mode`. Built-in OC2 always uses `/root/.oc-opencode2/{config,data,state,cache}` with `OPENCODE_CONFIG_DIR=/root/.oc-opencode2/config/opencode` and `OPENCODE_DB=/root/.oc-opencode2/data/opencode/opencode.db`. Never assume OC2's source lives in the isolated directory merely because its target does. Custom XDG/OPENCODE overrides are unsupported until their roots are explicitly inventoried.

Local evidence: [bridge](../../../lib/termux/bridge.dart), [shared installer](../../../lib/termux/opencode_ubuntu_setup.dart), [built-in server paths](../../../lib/builtin/builtin_linux.dart), [project persistence](../../../lib/builtin/builtin_folders.dart).

## Item decisions

| Item | Managed source | Decision and reason |
|---|---|---|
| Projects and repositories | `/root/projects`, including hidden files and ordinary in-tree `.git` directories | **Migrate selected projects** into the retained project bind, without overwriting unrelated targets. Treat every project as confidential: `.env`, embedded tokens and Git remote URLs may exist. Do not print names/contents in diagnostics. Reject unsafe links and external Git worktree references rather than silently lose dependencies. Keep source unchanged. |
| OpenCode global config, agents, skills, commands | OC1 `.config/opencode`; OC2 selected default/isolated config | **Offer**, with version/runtime match and explicit review. Config can contain secrets, shell commands, local paths and plugins. Copying it into an active config directory can execute plugins or enable MCP processes; a safe initial implementation may retain it as a private export for review instead. Exclude generated dependency caches and service-discovery credentials. |
| Project OpenCode/MCP config | Project `.opencode`, `opencode.json` / `.jsonc` | **Migrate with its explicitly selected project**, preserving bytes; warn that local commands and absolute paths can need repair. Do not run imported project config as part of checksum verification. |
| OC1 provider authentication | `/root/.local/share/opencode/auth.json` unless overridden | **Offer only through a private transfer**, destination 0600 and parents 0700; otherwise **require sign-in again**. Never include in diagnostics, notifications, shared plaintext archives or stdout. Environment-only auth is not a portable file. |
| OC2 provider authentication | Active `opencode.db` credential table; legacy `auth.json` may remain | **Require sign-in again** for this bounded slice. The legacy file is only a migration input and may be stale. A raw session database backup also contains credentials; do not label it a harmless session export. No private-schema credential extraction. |
| Sessions and OpenCode data | Active `opencode.db` plus WAL/SHM; old `storage/` JSON may remain; data `repos/`, snapshots and attachments may be referenced | **Export only**, not automatic restore/resume. Same runtime and exact pin are necessary but not sufficient: live copying does not provide a consistent database snapshot or prove referenced artifacts are complete. Use supported per-session export into private storage when offered. No claim that OC1 exports import into OC2 or vice versa. Keep original history usable through the retained Termux profile. |
| MCP global configuration / auth | OpenCode config plus runtime-owned auth/state | **Offer reviewed config; sign in again** for MCP auth. Commands referring to Termux `$PREFIX`, Android paths, tools or sockets will not carry over unchanged. Never auto-start imported MCP commands during verification. |
| Git identity and settings | `/root/.gitconfig`, `/root/.config/git/config` | **Offer reviewed export**, not blind activation. Includes and credential helpers can reference missing paths or run commands; remote URLs and extraheaders can contain secrets. Project `.git/config` remains private project content. |
| Git credentials | `/root/.git-credentials`, credential helper stores, environment/agent | **Skip automatic copy; sign in again**. Helpers/keyrings are runtime-specific; copying global config does not migrate them. Never export a running agent socket. |
| SSH | `/root/.ssh` (and separate Termux `~/.ssh` if the user used native Termux SSH) | **Offer only a separate explicitly selected private export**, or create/re-authorize keys in Ubuntu. Private keys 0600, directory 0700. `config` can contain commands and host-specific paths; skip sockets/controlmasters and do not auto-activate configuration. Native Termux home is not implicitly included in managed-Ubuntu migration. |
| Shell dotfiles | `/root/.bashrc`, `.profile`, `.zshrc`, etc. | **Optional reviewed export**, never source automatically. Termux path assumptions, startup commands and embedded secrets make automatic activation unsafe. Shell histories and environment dumps are **skipped**. |
| AI Team projects / state | `/root/aiteam` (city, origins), `/root/.gc`, `/root/.dolt`; Termux manager `~/.oc/aiteam`, legacy city; project worktrees | **Offer private export; skip automatic live-state restore**. Reinstall pinned tools through setup, re-create runtime supervision. Do not copy PID/lock/socket/process state or auto-resume autonomous work. Projects with origins under `/root/aiteam/origins` need their matching repositories preserved before they are claimed complete. |
| Toolchains, downloaded runtimes, caches, logs, manager/password/PID files | `/opt`, `/usr`, `.cache`, Termux `~/.oc` operational state | **Skip**. Setup v2 reinstalls selected pinned components; source service credentials and process identities must not become the new server's credentials. Logs can contain prompts, file contents and credentials. |

## Session and credential evidence at the exact tags

OC1 **1.18.32** sessions call `Database.Service`; they are not adequately represented by the old JSON `storage/` tree. Its database initializes WAL mode and applies migrations. `storage/storage.ts` retains legacy JSON migration logic. These facts make a live tar of the data directory insufficient as a proven import procedure. Sources: [OC1 session implementation](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/opencode/src/session/session.ts), [OC1 database](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/core/src/database/database.ts), [legacy storage](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/opencode/src/storage/storage.ts).

OC1 auth writes `auth.json` under its data directory with 0600 permissions. Its global roots follow XDG variables. Sources: [OC1 auth](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/opencode/src/auth/index.ts), [OC1 global roots](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/core/src/global.ts).

OC2 **2.0.10** has a `credential` table whose JSON value holds keys/OAuth data. Its migration imports legacy `auth.json` into that table once and skips an already represented integration. An old auth file therefore cannot be treated as a fresh authoritative list. The database also uses WAL and migrations. Sources: [credential table](https://github.com/anomalyco/opencode/blob/v2.0.10/packages/core/src/credential/sql.ts), [legacy credential migration](https://github.com/anomalyco/opencode/blob/v2.0.10/packages/core/src/database/migration/20260805200742_import_legacy_credentials.ts), [OC2 database](https://github.com/anomalyco/opencode/blob/v2.0.10/packages/core/src/database/database.ts), [database path selection](https://github.com/anomalyco/opencode/blob/v2.0.10/packages/cli/src/database-path.ts).

Both tags have supported session-export commands; their existence proves an export route, not interchangeable import schemas or safe resumption of running tools. Exports can contain sensitive transcripts and files even when they do not copy the credential table. Sources: [OC1 export](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/opencode/src/cli/cmd/export.ts), [OC2 session export](https://github.com/anomalyco/opencode/blob/v2.0.10/packages/cli/src/commands/handlers/session/export.ts).

## Transfer boundary

The app cannot read Termux's private directories. Inventory/packing must run as Termux through `RUN_COMMAND`; the app receives only bounded metadata and archive bytes via an authorized transfer endpoint. A shared-storage location is not suitable for an unencrypted archive: even projects can contain credentials. Prefer an authenticated, one-use loopback stream into app-private staging, with a checksum, bounded bytes/files/time and cancellation. No Termux data is deleted. A lost callback must never be treated as proof that a Termux command stopped.

Space checks account for Termux's archive (when materialized), app-private incoming archive, unpack staging, and final destination; shared filesystem capacity must not be double-counted as two independent free pools. Per-item sizes are data, not permission to disclose filenames. Refuse archive traversal, links escaping the selected tree, devices/FIFOs/sockets, and unbounded expansion. Import into new staged paths, verify, then publish without overwriting unrelated existing content. Durable checkpoints contain IDs, sizes, checksums and fixed error codes only, never credentials or command output.
