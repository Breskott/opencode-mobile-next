# Control-plane research sprint — executive summary (2026-09-10)

Research for the "OpenCode Mobile — AI Development Control Plane" BRD. Documents only; no app code was changed. Every claim about Gas Town / Gas City / Beads in this folder is either cited (URL) or marked **unverified**. Full findings: [gas-town-findings.md](gas-town-findings.md). Proposal: [architecture-proposal.md](architecture-proposal.md). Plan: [sprint-plan.md](sprint-plan.md). Owner decisions needed: [open-questions.md](open-questions.md).

## What Gas Town / Gas City actually is today

- **Gas Town** (`gastownhall/gastown`, Go, MIT, v1.2.1 on 2026-06-06, ~18k stars) is Steve Yegge's original multi-agent workspace manager: Mayor / Polecats / Witness / Refinery / Deacon / Dogs / Crew roles, tmux-driven sessions, Beads for durable work, a Bors-style merge queue ("Refinery"). Its only network surface is an htmx web dashboard (`gt dashboard`, loopback:8080 by default) whose `/api/*` handlers **shell out to `gt`/`bd`/`gh`** behind a CSRF token; its "SSE" is a 2-second hash poll. It is not a typed API a mobile client should build on.
- **Gas City** (`gastownhall/gascity`, Go, MIT, v1.4.1 on 2026-08-15, launched 2026-04-24) is the successor SDK the same team extracted from Gas Town. The Gas Town roles are now a *pack* (configuration); the engine is six primitives (Agent, Bead, Formula, Rig, Pack, Event). Critically, the `gc supervisor` exposes a **typed HTTP + SSE control plane described by an OpenAPI 3.1 document** (`/v0/...`, 164 operations): cities, rigs, agents (with `provider`, `model`, `context_pct`, `active_bead`), beads (CRUD, deps, ready, graph), **runs** (`/runs`, `/runs/{id}/steps`, cancel; status enum `pending|active|waiting|canceling|completed|failed|canceled|skipped`), sessions (peek, transcript, SSE stream, pending interaction + respond, nudge/submit, stop/kill/wake), convoys, formulas, orders, mail, usage (`cost_usd_estimate`), and a sequence-numbered event bus with `Last-Event-ID` resume. This is the surface the BRD assumed existed — and it does, but only in Gas City, not Gas Town.
- **Beads** (`gastownhall/beads`, Go, MIT, v1.2.2) is now **Dolt-backed** (embedded Dolt in `.beads/embeddeddolt/` by default; `.beads/issues.jsonl` is an export, not the source of truth). `bd --json` everywhere, `--readonly`, an opt-in events journal (`bd events tail --follow`, JSONL with `seq`), and a Python MCP server (`beads-mcp`). Gas City wraps `bd` so a client should not need to touch it directly.

## Biggest gaps between the BRD and reality

1. **"Gas Town-compatible" is the wrong target.** Gas Town has no client-grade API; Gas City does. The BRD should say "Gas City supervisor API (v0)". The Gas Town roles the BRD's glossary maps (Polecat, Witness, Refinery…) are pack conventions in Gas City, not API objects — the API talks about agents, sessions, beads, runs, convoys.
2. **Security model is inverted from what a phone needs.** Gas City's read plane is *fully unauthenticated by design* (network/TLS front required); mutations need a `X-GC-Request` header plus, on a hardened bind, a **signed ed25519 write grant** minted by an operator-side tool. Non-loopback binds are read-only unless `allow_mutations`. Neither matches the app's Basic-auth profile model. A phone must sit behind Tailscale and either (a) stay read-only, or (b) go through a small host-side authority that verifies Tailscale identity and mints grants.
3. **Gates are thinner than the BRD's "Decision Requests".** Gas City has (a) per-session *pending interactions* (permission prompts with `kind/prompt/options/request_id`, answered via `respond {action, text}`), (b) *gate beads* synthesized by formula `[steps.gate]` that block a step until the bead is closed — but the `human`/`gh:pr`/`timer` gate *types* are "doc-comment vocabulary… no bundled watcher acts on them", and (c) mail. There is no structured multiple-choice "architecture decision" primitive routed back to a workflow; the app would model that as a gate bead + mail, or as a session interaction.
4. **No diff / changes / verification API.** Gas City tracks work and sessions, not code review. Changes must come from the OpenCode server's VCS/worktree surface (already in `ServerGateway`) or from git on the host. "Verification" is a formula `check` loop, not a queryable state.
5. **Merge is pack behaviour.** `gc sling` accepts `merge: direct|mr|local`, but the Bors-style queue (`gt mq`) "lives in the pack and formulas, not a generic platform namespace". Merge readiness for the BRD's "Ready to merge" card has to be derived (beads closed + MR bead/PR state), not read.
6. **Planning from an objective is not an API.** "Objective → plan → work graph" is what the Mayor agent (a pack) does in a session; the API just lets you sling text to an agent and watch beads appear.

## Recommended integration shape

- Add `OrchestrationGateway` (`lib/domain/orchestration_gateway.dart`) beside `ServerGateway`, with the same style: composed role interfaces, a flat `OrchestrationCapabilities` value class, `LiveEventChannel` streams, capability-gated UI. Product model = Project(Rig) / Run / Work(Bead) / Agent / Gate / Activity event.
- First provider adapter: **Gas City supervisor API, direct, read-only**, over Tailscale, in `lib/orchestration/adapters/gascity/`. Reads and SSE need no credential; the app just needs a base URL and optional city name. This alone delivers the Workspace summary, Run detail, Work list, Agents list and Activity aggregation.
- Second step: a **thin host-side sidecar** ("control-plane front", Go or Python, ~1 process) that fronts the supervisor for the phone: Tailscale-identity check → mints write grants → forwards mutations; adds `/changes` (git diff per bead/worktree) and `/verification` (formula check results) which Gas City does not expose. Reads keep going straight to the supervisor. Do not build a full proxy of the 164 operations.
- Keep a fixture server in `tool/qa/gascity_fixture/` (Python stdlib, like the Codex fixture) that serves a frozen subset of the OpenAPI shapes + an SSE event log, so the vertical slice ships without a Gas City install.

## Top risks

- **API is `v0` and moving fast** (pushed daily; spec version 0.1.0). Pin the spec snapshot in `contracts/` like `opencode2-openapi-beta-18600.json`, generate DTOs, and treat every read as "may be shaped differently next release".
- **Host requirements are heavy**: tmux, git, jq, Dolt ≥ 2.1.0 + `bd` ≥ 1.0 + `flock` (or `GC_BEADS=file`), a Go 1.26 CGO/ICU build if not using Homebrew. Termux hosting is **unverified** and probably out of scope for v1.
- **Unauthenticated reads leak everything** (bead bodies, transcripts, events) to anyone on the tailnet who can reach the port. The app must refuse plain `http://` to non-loopback hosts (Gas City's own `gc` client does) and show server identity clearly.
- **Product vocabulary drift**: the BRD's glossary is Gas Town's; users installing Gas City will see `gc`, cities, packs, convoys, runs. The UI must translate from Gas City's actual DTOs, with the Gas Town names as aliases only.
- **Owner intent is unknown**: nobody has stated which orchestrator will actually run (Gas City vs ralph-tui vs plain OpenCode subagents). The vertical slice is designed so the fixture, not a real orchestrator, is the first dependency.
