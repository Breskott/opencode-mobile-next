# Storage cleanup scope — 2026-09-13

Finish line: preserve a useful standard-Termux inventory while restricting every destructive cleanup to explicitly regenerable caches, confirmed by the user and guarded again in the backend. Non-goals: tool/package uninstall, alternate Termux forks, whole-device storage coverage, scan performance redesign, or running cleanup on a real device.

The existing scan uses standard Termux home/prefix locations and supports current and legacy `opencode-ubuntu` rootfs layouts. It is not tied to a personal username or particular project names. Its breakdown covers known locations, while its total measures Termux home and prefix, not the whole phone or just the OpenCode server. Project locations outside the managed `root/projects` tree are included only in the total when inside those Termux roots. Project build-name inventory overlaps project totals; categories are not an additive disk accounting ledger.

The original deletion boundary trusted broad categories and folder basenames. This could delete team databases, shared scratch, tools or user-authored files inside a folder called `build`. These remain visible but are now read-only, including direct calls and old reports. Only the exact managed-root Gradle `caches` and Termux/managed-root npm `_cacache` directories remain eligible. Broad `.cache`, `.npm`, `.pub-cache`, Gradle wrappers, analyzer folders, SDKs and temporary folders are excluded.

Cleanup resolves trusted Termux anchors, then checks the exact path, canonical parents and owning UID. A replaced cache/rootfs parent or cache symlink is refused. Scans and cleanups share an operation lock; active build and npm install processes block cleaning. This is conservative shell-level protection, not a transaction against arbitrary concurrent filesystem mutation by another process with the same Termux UID.

Reports carry cleanup policy version 2. Older reports require rescanning. Cleanup measures sizes again, counts only observed removed bytes, keeps refused/partially removed manifest entries and marks the persisted report stale before mutation. The screen preserves that old measurement with a rescan notice and disables further cleanup. Every cleanup, even below 1 GiB, requires confirmation. Sizes use the existing `du -sb` apparent-byte measurement; the result says “Removed”, rather than claiming a matching increase in filesystem free space. A failed measurement never authorizes deletion.
